# Yggdrasil Desktop App — Plan & Status

Durable copy of the planning doc for the desktop client, so the roadmap survives past any one session. Update the status line per phase as work lands.

**Status: v1 scope complete** — all 6 phases below done (chat + agent management + settings + cross-platform packaging config). Remaining open items are called out inline per phase (no `agents.update`/`delete` RPC yet, real app icon/branding, Win/Mac packaging untested on this dev machine, asar re-enablement) — see "Future" at the bottom for what's deliberately out of scope.

## Context

Yggdrasil already has a gateway (`@yggdrasil/gateway`) that any client talks to over WebSocket RPC, with two existing clients — `app-tui` (Ink/terminal) and `web-console` (React/Vite browser admin console). This package, `app-desktop`, is a third client: a native desktop app (Windows/Mac/Linux) with a Cursor/Grok-bot-style UX — agent picker, multi-session chat, tool-call cards, approval prompts, agent management. It's a new client on top of the existing gateway; no kernel/pipeline/harness/provider changes needed.

Decisions made:

- **Shell: Electron**, not Tauri. Everything in this repo is Node/TS; Electron's main process is just Node, so it boots `@yggdrasil/gateway`-backed `@yggdrasil/cli` directly — no cross-language sidecar packaging.
- **Scope v1: chat + agent management**, not a full IDE. No file tree, no diff viewer, no code editor — that's a possible future phase, not v1.

## Architecture (as built)

- `packages/app-desktop/` — `electron-vite` project: `src/main` (app lifecycle, gateway lifecycle), `src/preload` (minimal `contextBridge` surface), `src/renderer` (React + TS UI).
- **Gateway lifecycle** (`src/main/gateway.ts`): probes `http://127.0.0.1:18789/` for an already-running gateway; if none, spawns `@yggdrasil/cli`'s `gateway` subcommand as a child process under `ELECTRON_RUN_AS_NODE=1` (Electron's bundled Node, no external Node install required), with `YGGDRASIL_WORKSPACE` pointed at `app.getPath("userData")` (OS-appropriate per-app data dir, not tied to any dev workspace). Seeds a minimal `yggdrasil.config.json` there on first run only, with `plugins.load.paths` pointing at this package's own `node_modules/@yggdrasil` — required because pnpm's isolated `node_modules` means plugin discovery (which scans `<workspaceRoot>/packages`, `<workspaceRoot>/node_modules/@yggdrasil`) would otherwise find zero providers/tools/harnesses when `workspaceRoot` is a data dir outside the monorepo. This path assumes a dev/unpacked layout (`app.getAppPath()`) — confirmed correct for the packaged app too in phase 6 (packaging deliberately ships unpacked, no asar; see that section).
- **Renderer** talks to the gateway exactly like `web-console`: opens its own WebSocket via `@yggdrasil/client-web`'s `GatewayClient`/`GatewayProvider`, no IPC-mediated data layer. `preload` only exposes `getGatewayUrl()` (native/non-browser concerns only).
- **`@yggdrasil/client-web`** (new shared package) — `GatewayClient` + `GatewayProvider`/`useGateway()` React hook, extracted out of `web-console` so both browser-based clients (`web-console`, `app-desktop`) share one implementation instead of duplicating it. `GatewayProvider` takes an optional `wsUrl` prop (`web-console` omits it and gets `defaultWsUrl()` from `window.location`; `app-desktop` must pass it explicitly since its renderer isn't served from the gateway's origin).
- No new state-management library — hooks/local reducers, consistent with `web-console`/`app-tui`.

## Post-v1 additions

- ✅ **Fixed misleading `chat.send` timeout** — user-reported bug: local models (e.g. Ollama `qwen2.5-coder:7b`) can take longer than `GatewayClient`'s default 30s `call()` timeout, so the UI showed `Error: Timeout: chat.send` even though the turn was still running server-side and its real reply landed seconds later via the `chat.final` event (the RPC promise and the event stream are independent — see `ChatView.tsx`'s `send()`). Fixed two ways: (1) `@yggdrasil/client-web`'s `useGateway().call` now accepts an optional `{timeoutMs}` (threaded through to `GatewayClient.call`, backward compatible — `web-console`'s call sites are unaffected), and `chat.send` now uses a 180s timeout; (2) if it times out anyway, the UI no longer shows a scary "Error:" message for that specific case (the reply still arrives via the event listener) — it just refreshes the session list quietly instead.
- ✅ **Settings restructured into sidebar + panel** — `SettingsView.tsx` now a nav (Agent/Harness/Channels) + detail panel layout instead of one long scrolling modal, matching a real settings-app pattern. Existing fields moved as-is into `settings/sections/{AgentSection,HarnessSection,ChannelsSection}.tsx`, each a thin `{config, setConfig}` presentational component — no behavior change, same `config.get`/`harnesses.list`/`providers.list`/`config.patch` RPC calls already verified in the original settings phase. Single global Save/Close footer still applies across all sections (one underlying config object, not per-section saves).
- ✅ **Composer toolbar (agent + model pickers)** — below `ChatInput`, `ComposerToolbar.tsx` shows two pill selects: Agent (moved out of the sidebar, which previously had a separate "Agent" dropdown — consolidated into one bottom bar like Cursor/ChatGPT) and Model (populated from `providers.list`, spans every provider not just the active agent's own). Picking a model sets a per-session `modelOverride` in `chatReducer.ts` (cleared automatically on agent switch) that `ChatView.tsx`'s `send()` forwards as `chat.send({..., provider, model})`.
  - **Required a real backend change, not just UI** — `chat.send` previously only accepted `agentId`; there was no way to influence which provider/model actually answered independent of the agent's own stored config. Added `provider`/`model` passthrough in `packages/gateway/src/methods.ts`'s `chat.send` handler (mirrors the existing `agentId` → `metadata` pattern) and made `packages/pipeline/src/turn-kernel.ts`'s `dispatchToHarness` prefer `message.metadata.provider`/`.model` over the resolved agent's own `provider`/`model` when present — the agent's config itself is never mutated, this is purely a per-turn override. Regression test at `packages/pipeline/src/pipeline.test.ts` (mock harness keyed to a distinct provider id, asserts the override — not the agent's own `builtin`/`echo` — is what gets selected and passed through).
  - Verified against the real running gateway: sent `chat.send` with `provider: "ollama", model: "qwen2.5-coder:7b"` against the `default` agent (whose own config is `openai-compat`/`gpt-4o-mini`) — `turn.start`'s payload showed `harnessId: "llm"` (harness-llm, selected because the override's `provider: "ollama"` matched), not the agent's own provider. Fell back to `builtin-echo` for the final reply only because no local Ollama server is reachable on this dev machine — expected, and itself proof the override reached a real network attempt rather than being silently ignored.
- ✅ **Session context menu** — right-click a session in the sidebar for Copy ID / Rename / Delete (`chat/SessionContextMenu.tsx`, wired through `SessionSidebar.tsx` → `ChatView.tsx`). Rename uses the existing `sessions.patch({sessionKey,title})` RPC, Delete uses `sessions.reset({sessionKey})` — note `SessionStore.reset` (`packages/sessions/src/store.ts`) actually `unlink`s the session file, i.e. it's a real delete despite the "reset" name, not a message-clear. No gateway/store changes needed, both methods already existed. Deleting the active session falls back to a fresh new session so the chat pane never shows a dangling deleted one. Verified against the real gateway with the exact params the UI sends: rename persists and shows in `sessions.list`, delete removes it from `sessions.list` and `sessions.get` returns `null` after. `web-console` intentionally untouched (has its own separate Sessions page).

## Projects (multi-window, per-project agents, orchestrator delegation, file tree)

**Status: all 4 phases done.** Restart any already-running project window to pick up new gateway builds (a running gateway keeps whatever tools/RPC methods it loaded at boot).

Big post-v1 initiative — full context/decisions in the plan-mode doc this was designed from (`ya-tenemos-una-arquitectura-binary-owl.md`, since superseded by this status). Summary: a **Project** wraps a folder (its own `yggdrasil.config.json`/agents/sessions); opening one spawns a **new OS window**. Confirmed with user: project creation = pick an existing folder *or* create a new one; file tree is browse-only (no in-app editor, stays out of full-IDE territory); orchestrator delegation is prompt-driven (a generic `invoke_agent` tool, not auto-discovery).

Key finding that de-risked this: `ensureGateway()` already spawns each gateway as a **separate OS child process**, not in-process — so the kernel-registry/session-store `globalThis` singletons never collide across projects. Multi-project = multi-child-process is the natural extension of the existing architecture, not a rework of it. Per-project agents also need **zero backend schema change** — `agents.create`'s `scope: "local"` already writes into whatever `workspaceRoot` the active gateway has.

## Right panel file viewer + @ mention / drag-drop attachments

**Status: done.** Context/full design in the plan-mode doc this was built from (`ya-tenemos-una-arquitectura-binary-owl.md`).

- **Real bug fixed first**: `spawnGatewaySubprocess` (`main/gateway.ts`) never set `cwd` on the spawned gateway subprocess — it inherited Electron's own directory, not the project. `tool-system`'s `read_file`/`list_directory`/`write_file` resolve relative paths purely off `process.cwd()`, so every agent's file tools have been silently pointed at the wrong directory since Projects phase 1. One-line fix: `cwd: workspaceRoot` added to the `spawn()` call.
- **Backend**: `fs.read({relativePath})` and `fs.search({query,limit?})` added to `packages/gateway/src/methods.ts`, same sandboxing pattern as `fs.list` (workspaceRoot-scoped, `..`-escape rejection). `fs.search` walks the tree skipping `node_modules`/`.git`/`dist`/`.yggdrasil`, capped at 5000 scanned entries and (by default) 50 results. 12 tests total in `fs-methods.test.ts` (4 fs.list + 4 fs.read incl. truncation + 4 fs.search incl. the noise-dir skip).
- **Right panel**: `files/FileContentPanel.tsx`, third `chat-shell` column, opens on clicking a file row in the tree (`FileTreeNode`'s files now call `onOpenFile` instead of being inert; directories still just expand). Read-only `<pre>` view, no syntax highlighting — stays inside the "browse, don't edit" scope the file tree already established.
- **Attachments**: `ChatView` owns `attachedFiles` state. `FileTreeNode` rows are `draggable` (custom `application/x-yggdrasil-file` MIME payload) for both files and directories. `ChatInput.tsx` rewritten: chip row above the textarea, `@(\S*)$` detection driving a debounced `fs.search` dropdown (↑↓/Enter/click), `onDragOver`/`onDrop` reads the same drag payload — both paths call the same `onAttach`.
- **Send-time behavior — the important design call**: attachments are **not** sent as bare paths for the model to maybe go fetch via a tool call. `ChatView.send()` resolves each attachment right before sending — a file's real content via `fs.read`, a folder's one-level listing via `fs.list` — and inlines clearly-delimited blocks (`--- path ---\n<content>`) into the outgoing `chat.send` message text. No new RPC param, no metadata channel. This matches how Cursor/Claude/VS Code actually behave (instant inlined context) rather than hoping the model decides to call a tool — while the model's own `read_file`/`list_directory` tools (now correctly `cwd`-scoped) remain available for anything beyond what got inlined. The user's own chat bubble still shows their clean typed text, not the dumped file content — only the message actually sent to the gateway carries the attachment blocks. `attachedFiles` clears after a successful send.

## Post-Projects bugfix: config.patch silently deleted agents

**User-reported**: created an agent for the `mross-portfolio` project; it wasn't there afterward. Confirmed directly — that project's `yggdrasil.config.json` on disk had no `agents` field at all.

**Root cause**: `config.patch`'s gateway handler (`packages/gateway/src/methods.ts`) wrote `patch.agents` straight through to `writeConfigFile`, and `mergeConfig`'s merge rule for `agents` is full-replace, not union (`agents: override?.agents ?? base.agents`). `patch.agents` is whatever the client had in memory from its last `config.get` — e.g. `SettingsView.tsx` fetches it once when the modal opens. So: open Settings, create an agent via `AgentManager` (a completely different flow, writes correctly via `agents.create`/`createAgent`), then save Settings for literally any unrelated reason (a harness policy tweak, a channel toggle) — the stale `agents` snapshot from before the agent existed gets written back, silently erasing it. No error, no warning; the create appeared to succeed and the UI showed the agent right up until the next patch.

**Fix**: `config.patch`'s handler now re-reads the current on-disk `agents` and merges by id (`Map` keyed by id, patch entries override/add, anything only on disk survives) before writing, instead of trusting the client's array as complete. Also fixed the in-memory `ctx.config` update on the same request to use the merged list rather than the raw patch, so a gateway process's live state doesn't drift from what's on disk. Regression test in `packages/gateway/src/config-methods.test.ts` reproduces the exact scenario (an agent present on disk but absent from the patch's snapshot) and asserts it survives, with an edit to a different agent in the same patch still applying correctly. Found and fixed a real test-isolation gap in the same file while writing it — `config-methods.test.ts` didn't mock `homedir()` like `agents-methods.test.ts` already does, so a strict assertion on the returned agent list picked up whatever real global agent happens to exist in `~/.yggdrasil/agents.json` on the dev machine; added the same mock.

**Not recoverable**: the specific agent the user created for `mross-portfolio` is gone — it only ever existed in that project's config file, which is what got overwritten. They'll need to recreate it; it won't happen again with this fix in place.

## Terminal tab (multi-pane node-pty terminals)

**Status: done.** Chat area became a tab container — `chat/MainTabs.tsx`, Chat + Terminal both permanently mounted (only `display:none` toggles, never unmounted — switching tabs must not lose chat state or kill running shells).

Terminal tab: real interactive PowerShell (Windows) via `node-pty`, managed in `main/terminals.ts` (a `Map<TerminalId, {proc, exitListener}>`, no classes) + IPC (`terminal:create/write/resize/dispose/getLayout/saveLayout`, plus push events `terminal:data`/`terminal:exit`). **Two real bugs found and fixed during this phase** (both load-bearing for "both tabs persist" being true, not just visually true):
- **Remount-kills-session**: React force-remounts a leaf's subtree whenever the JSX element type at that tree position changes (e.g. a leaf gaining a sibling via split) — no `key` prevents this. A portal-based first attempt still raced (the old DOM container gets destroyed in the same commit a portal from the previous render still targets). Fixed by hoisting the actual `Terminal`/`FitAddon`/subscriptions into a `useRef`-held `TerminalRegistry` Map in `TerminalContainer` (survives remounts by construction, not by preventing them) — `TerminalPane` re-attaches (`container.appendChild(entry.term.element)`) rather than recreating on every mount.
- **Stray "process exited" false positive**: `disposeTerminal()` killed the pty while its `proc.onExit` listener (which sends the `terminal:exit` IPC event) was still attached — a defensive re-create or React's mount→cleanup→mount could kill an old process whose exit event arrived *after* a fresh replacement was already spawned under the same id, misread by the new pane as itself exiting. Fixed by capturing `proc.onExit`'s `IDisposable` and calling `.dispose()` on it before `.kill()` — a deliberate dispose is now silent, only genuine spontaneous exits notify the renderer.

**Known accepted limitation, not fixed**: node-pty 1.1.0's Windows grandchild-process cleanup helper (`conpty_console_list_agent.js`) throws `AttachConsole failed` on some dispose paths — confirmed (by reading `windowsPtyAgent.js`) that the *primary* `kill()` of the spawned process itself is synchronous and unaffected; only orphaned grandchildren (rare) might not get cleaned up. Upstream rough edge, not patched.

**Verified via Playwright `_electron`** (real launch, real clicks — `page.click(".xterm-screen")` needed for real xterm focus, DOM `.click()` doesn't focus its hidden textarea): split horizontal/vertical → independent shells (different `$PID`), drag-resize live, switch to Chat and back → scrollback + a long-running command both survived, close a pane → the rest keep working and the process is actually gone.
