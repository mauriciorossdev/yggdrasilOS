# @yggdrasil/tools-sdk

## Purpose

Defines the shared type contract and helper (`defineTool`) that every "tool" in
Yggdrasil is built from. A tool is a single callable capability an LLM can
invoke (read a file, get the weather, run a shell command, etc). This package
has no runtime behavior of its own beyond `defineTool` — it exists so that
tool authors, the runtime that executes tools (`@yggdrasil/tools-runtime`),
and the harness that offers tools to the model (`@yggdrasil/harness-llm`) all
agree on the same shape without depending on each other directly.

This is the lowest-level package in the tools stack. If you are writing a new
tool, this is the only package you strictly need to import.

## Public API

From `src/index.ts` (re-exported from `src/types.ts`):

```ts
export function defineTool(def: AgentToolDefinition): AgentToolDefinition;

export type AgentToolDefinition = {
  name: string;
  description: string;
  parameters: ToolParameterSchema;
  requiresApproval?: boolean;
  riskLevel?: ToolRiskLevel;
  execute(ctx: ToolContext, args: Record<string, unknown>): Promise<unknown>;
};

export type ToolContext = {
  sessionKey: string;
  config: unknown;
};

export type ToolParameterSchema = {
  type: "object";
  properties: Record<string, { type: string; description?: string }>;
  required?: string[];
};

export type ToolRiskLevel = "safe" | "moderate" | "destructive";
```

`defineTool` is a thin normalizer, not a builder — you pass it a complete
`AgentToolDefinition` and it hands back essentially the same object, with one
rule applied: if `riskLevel === "destructive"` and you did not explicitly set
`requiresApproval: false`, it forces `requiresApproval: true`. That's the
entire implementation (see `src/types.ts`). It exists so destructive tools
can't accidentally skip the approval gate just because the author forgot to
set the flag.

## Depends on

Nothing in the workspace. No runtime dependencies at all (see
`package.json`) — it only depends on TypeScript at build time.

## Used by

Everything that defines or consumes a tool imports the `AgentToolDefinition`
type or `defineTool` function from here:

- `@yggdrasil/tool-builtin`, `@yggdrasil/tool-system`, `@yggdrasil/tool-weather` — first-party tool implementations bundled in this monorepo, all built with `defineTool`.
- `@yggdrasil/tools-runtime` — registry/execution/OpenAI-conversion logic is typed against `AgentToolDefinition` and `ToolContext`.
- `@yggdrasil/sdk` — `plugin.ts` re-exports `AgentToolDefinition` as part of the plugin API surface (so `api.registerTool(...)` is typed); `harness.ts` uses `ToolRiskLevel`; `provider.ts` uses `ToolParameterSchema`.
- `@yggdrasil/harness-llm` — `tool-loop.ts` and its tests type tool calls against `AgentToolDefinition`.
- `packages/cli/templates/tool` — the scaffold generated by `create-plugin --kind tool` imports `defineTool` from here.
- Third-party/example tool plugins outside `packages/`: `extensions/tool-datetime`, `extensions/tool-destructive-demo`, `extensions/my-tool`.

## Configuration

None. This package has no config surface — `ToolContext.config` is just a
pass-through of whatever the caller (harness, gateway) supplies at
execution time.

## Extending / what's safe to change

This package is the contract. Changing `AgentToolDefinition`'s shape is a
breaking change for every tool package and every extension in the monorepo —
treat it as a last resort, and if you do it, grep the whole tree (`packages/`
and `extensions/`) for `AgentToolDefinition` and `defineTool` before touching
anything.

**How to add a brand-new tool** (this is the pattern every package below
follows):

```ts
import { defineTool } from "@yggdrasil/tools-sdk";

export const myTool = defineTool({
  name: "my_tool",              // snake_case, see below
  description: "One sentence the model uses to decide when to call this.",
  riskLevel: "safe",            // "safe" | "moderate" | "destructive"
  parameters: {
    type: "object",
    properties: {
      input: { type: "string", description: "..." },
    },
    required: ["input"],
  },
  async execute(ctx, args) {
    // ctx.sessionKey, ctx.config are available here
    return { result: "..." };
  },
});
```

Naming: **tool names must be snake_case** (`my_tool`, not `my-tool`). This is
a hard requirement noted in the repo's `AGENTS.md` — some LLM backends reject
hyphens in function/tool names, so a hyphenated name will work locally against
some providers and then fail against others.

Risk levels and approval, concretely:

- `riskLevel: "safe"` — no side effects worth gating (reading, listing,
  computing). No approval prompt.
- `riskLevel: "destructive"` — the tool mutates state, runs arbitrary code, or
  is otherwise irreversible/dangerous (writing files, running shell commands).
  `defineTool` automatically sets `requiresApproval: true` unless you pass
  `requiresApproval: false` explicitly to opt back out.
- `requiresApproval` can also be set independently of `riskLevel` (e.g. a
  `"moderate"` tool you still want gated).
- The actual gate is enforced by the caller, not this package: `harness-llm`'s
  tool loop checks `def.requiresApproval || def.riskLevel === "destructive"`
  before executing a tool call, and if true, calls the harness's
  `approveTool` callback and blocks execution until it resolves. This package
  only carries the flags — it does not implement approval UI/flow itself.

Once you've written the tool with `defineTool`, it needs to be exposed to the
runtime somehow. See `@yggdrasil/tools-runtime`'s README for how tools get
discovered (builtin array vs. plugin registration vs. legacy `ToolFactory`),
and `@yggdrasil/tool-system` / `@yggdrasil/tool-weather` for worked examples
of packaging a tool as an installable plugin with a `yggdrasil.plugin.json`
manifest.
